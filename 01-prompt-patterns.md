**ЗАДАЧА**

Контекст:  
Микросервисная платформа кардиомониторинга. Врач работает через UI, который обращается к measurement-service по REST API. Аутентификация — OAuth 2.0. Авторизация по роли и области доступа проверяется на стороне measurement-service.

Методы:  
GET /v1/measurements  
POST /v1/measurements  
PATCH /v1/measurements/{id}  
DELETE /v1/measurements/{id}  
GET /v1/measurements/export

Роли:  
INTERN — чтение  
RESIDENT — чтение \+ создание  
ATTENDING — CRUD  
CHIEF — чтение \+ экспорт  
ADMIN — без доступа к клиническим данным

Бизнес-правила:

* INTERN/RESIDENT/ATTENDING — только свои пациенты (assignedDoctorId \= doctorId)  
* CHIEF — все пациенты своего departmentId   
* doctorId берётся из токена, поле в теле игнорируется  
* нет/просрочен токен → статус код 401  
* роль не разрешает метод → статус код 403  
* разрешения токена (scope) не соответствует операции → статус код 403  
* пациент вне области доступа → статус код 403

Цель:  
Проверить, что каждая роль может только то, что ей разрешено, и не может обойти ограничения.

### **Плейбук промптов**

### **1\. Few-shot prompting**

РОЛЬ: Ты QA-инженер, специализирующийся на тестировании безопасности API и разграничении прав доступа. 

ЗАДАЧА:  
Проанализируй предоставленные бизнес-правила и сгенерируй новые тестовые сценарии на проверку прав доступа. Используй следующие примеры как образец формата и логики. Опираясь на предоставленные входные данные и образцы, сгенерируй демонстрационный  набор из 4 новых сценария (по одному на каждый тип: Позитивный, негативный, граничный, репрезентативный). Строго соблюдай формат из примеров 1-4. Обрати внимание: 4 сценария — это демонстрация паттерна, а не полное покрытие безопасности.

ВХОДНЫЕ ДАННЫЕ:

* Контекст системы: {КРАТКОЕ\_ОПИСАНИЕ\_СИСТЕМЫ}  
* Роли: {СПИСОК\_РОЛЕЙ\_И\_ИХ\_ПРАВ}  
* Бизнес-правила: {СПИСОК\_БИЗНЕС\_ПРАВИЛ\_ДОСТУПА}

ПРИМЕР 1\. Позитивный сценарий  
Условие: Роль ATTENDING вызывает метод GET /v1/measurements для своего пациента.  
Ожидаемый результат: 200 OK. Возвращается список измерений.  
Риск: Отсутствует (штатное поведение).

ПРИМЕР 2\. Негативный сценарий  
Условие: Роль INTERN вызывает метод DELETE /v1/measurements/{id}.  
Ожидаемый результат: 403 Forbidden. Доступ запрещен.  
Риск: Неквалифицированный сотрудник удаляет медицинские данные.

ПРИМЕР 3\. Репрезентативный сценарий  
Условие: Врач CHIEF запрашивает экспорт данных (GET /v1/measurements/export) для своего отделения (departmentId).  
Ожидаемый результат: 200 OK. Выгрузка содержит данные всех пациентов отделения.  
Риск: Утечка данных при неверной настройке фильтрации по отделению.

### **2\. Self-Verification**

РОЛЬ: Ты независимый QA-ревьюер, специализирующийся на безопасности и разграничении прав доступа. 

ЗАДАЧА: Выяви негативные тестовые сценарии и потенциальные риски обхода прав доступа. Используй паттерн Self-Verification.

ВХОДНЫЕ ДАННЫЕ:

* Контекст системы: {КРАТКОЕ\_ОПИСАНИЕ\_СИСТЕМЫ}  
* Роли: {СПИСОК\_РОЛЕЙ\_И\_ИХ\_ПРАВ}  
* Бизнес-правила: {СПИСОК\_БИЗНЕС\_ПРАВИЛ\_ДОСТУПА}

ЭТАП 1\. ГЕНЕРАЦИЯ  
Сформируй первоначальный набор из 7 негативных тестовых сценариев на проверку прав доступа. Для каждого укажи: название, условие, ожидаемый результат (HTTP-код), риск.

ЭТАП 2\. ПРОВЕРКА  
Проверь свой первоначальный результат:

* Все ли роли (включая роли без доступа к данным) покрыты?  
* Проверены ли сценарии, где токен валиден, но не имеет нужного разрешения (scope)?  
* Есть ли проверки на подмену ID пользователя в теле запроса?  
* Есть ли дублирующиеся сценарии?
* Трассируемость: Каждый ли риск из Этапа 1 привязан к конкретному бизнес-правилу?

ЭТАП 3\. ИСПРАВЛЕНИЕ  
Исправь первоначальный результат на основании проверки:

* Добавь пропущенные сценарии (например, на токены и горизонтальный доступ).  
* Уточни ожидаемые коды ответов (401, 403, 404).
* Добавь в каждый сценарий ссылку на нарушаемое бизнес-правило (например: "Нарушает правило: INTERN — только чтение").
* Выведи итоговый список только с обоснованными проверками.

### **3\. Prompt Chaining**

РОЛЬ: Ты QA-инженер, специализирующийся на тестировании безопасности API и разграничении прав доступа. 

ЗАДАЧА: Выяви негативные тестовые сценарии и потенциальные риски обхода прав доступа. Используй паттерн Prompt Chaining. Выполни задачу через последовательность этапов. Результат каждого этапа используй как входные данные для следующего.

ВХОДНЫЕ ДАННЫЕ:

* Контекст системы: {КРАТКОЕ\_ОПИСАНИЕ\_СИСТЕМЫ}  
* Роли: {СПИСОК\_РОЛЕЙ\_И\_ИХ\_ПРАВ}  
* Бизнес-правила: {СПИСОК\_БИЗНЕС\_ПРАВИЛ\_ДОСТУПА}

ЭТАП 1\. Анализ требований  
Выдели все правила разграничения доступа (роли, владение ресурсом, разрешения (scope) токена).  
Присвой каждому требованию уникальный ID.

ЭТАП 2\. Анализ рисков  
На основании этапа 1:  
Определи потенциальные дефекты.  
Присвой каждому риску приоритет High / Medium / Low.

ЭТАП 3\. Тест дизайн  
На основании требований и рисков:  
Определи негативные сценарии (кто, к какому методу, с каким токеном обращается).  
Выдели проверки на подмену (ID пользователя в теле запроса).
Убедись, что каждый RISK-ID покрыт хотя бы одним сценарием.

ЭТАП 4\. Генерация тест-кейсов  
Сформируй итоговый набор тестовых сценариев.  
Для каждого укажи:

* Test ID
* Связанный REQ-ID и RISK-ID (Трассируемость)
* Название  
* Условие (Роль \+ Метод \+ Область доступа)  
* Ожидаемый HTTP-код  
* Потенциальный риск  
* Приоритет

ОГРАНИЧЕНИЯ:

* Используй только предоставленные требования.   
* Не галлюцинируй.   
* Если данных для генерации не хватает \- задай уточняющий вопрос.
