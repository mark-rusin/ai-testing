
# Плейбук промпт-инжиниринга для QA: Продуктовый фреймворк тестирования API безопасности

*Версия 1.0 · Продуктовый фреймворк автоматизации тестирования и аудита безопасности REST API*

---

## 1. Стандарт и архитектура плейбука

Настоящий плейбук представляет собой инженерное руководство по промпт-инжинирингу для специалистов по обеспечению качества (QA). В отличие от академических приемов демонстрации отдельных паттернов, данный фреймворк спроектирован для создания **переиспользуемых продуктовых инструментов**, применимых в ежедневном процессе разработки и тестирования программного обеспечения.

### 1.1. Паспорт карточки промпта (9-полевой стандарт)

Для обеспечения прозрачности и стандартизации каждая техника промпт-инжиниринга в данном плейбуке оформляется в виде инженерной карточки метаданных, включающей 9 фиксированных полей.

| Поле метаданных | Назначение и содержание |
|---|---|
| **Name** | Уникальный системный идентификатор промпта (например, `api-security-fewshot`) |
| **Purpose** | Продуктовая цель применения — какую конкретную задачу QA решает данный промпт |
| **Pattern** | Используемый паттерн промпт-инжиниринга (*Few-shot*, *Self-Verification*, *Prompt Chaining*) |
| **Input** | Состав и формат входных материалов (спецификации API, лог-файлы, матрицы прав) |
| **Variables** | Список динамических параметров в фигурных скобках `{...}`, подлежащих замене |
| **Expected Output** | Структура и формат ответа модели (таблица, JSON, интерактивный HTML) |
| **Constraints** | Защитные правила (Guardrails): отмена галлюцинаций, маскирование данных, пометки `UNKNOWN` |
| **Example** | Ссылка на демонстрационный эталонный кейс применения |
| **Version** | Версионирование шаблона, целевые LLM и дата последнего обновления |

### 1.2. Анатомия шаблона (5-блочная структура)

Тело каждого промпта (`Prompt Template`) строго структурировано по 5 смысловым блокам, что гарантирует точное исполнение инструкций языковыми моделями:

1. **# Роль** — задает экспертную позицию модели (Senior Security QA Engineer, QA Reviewer, Automation Architect).
2. **# Контекст** — содержит описание системы, роли, матрицу прав и динамические переменные `{...}`.
3. **# Задача** — поэтапный алгоритм действий, который модель должна выполнить.
4. **# Формат** — жесткие требования к структуре ответа (заголовки, таблицы, Markdown-колонки).
5. **# Ограничения** — правила безопасности, маскирование Bearer-токенов `***` и обработка отсутствующих данных.

### 1.3. Правила шаблонизации и динамические переменные

Для обеспечения универсальности промпты вынесены из рамок конкретных проектов. Все специфичные данные подставляются через переменные:
* `{project_context}` — наименование и назначение тестируемого микросервиса.
* `{target_methods}` — перечень проверяемых эндпоинтов и HTTP-методов (`GET`, `POST`, `PATCH`, `DELETE`).
* `{roles_and_permissions}` — ролевая модель (RBAC/ABAC) и описание доступов.
* `{business_rules}` — правила безопасности, ограничение областей видимости и требования к токенам.
* `{output_format}` — выбор целевого формата вывода (Markdown-таблица / Интерактивный HTML-чек-лист).

## 2. Карточка 1. Few-shot prompting (Генерация сценариев безопасности по образцам)

Паттерн Few-shot prompting позволяет модели мгновенно перенять требуемый стиль, уровень детализации и логику привязки рисков за счет демонстрации нескольких качественных эталонных примеров.

### 2.1. Паспорт карточки

Ниже приведен паспорт метаданных карточки `api-security-fewshot`, определяющий ее назначение и граничные условия:

| Поле | Значение |
|---|---|
| **Name** | `api-security-fewshot` |
| **Purpose** | Быстрое составление набора тестовых сценариев проверки прав доступа (RBAC/ABAC) по эталонным образцам с привязкой рисков |
| **Pattern** | Few-shot prompting (демонстрация на репрезентативных примерах) |
| **Input** | Описание системы, список ролей, бизнес-правила доступа и целевые методы API |
| **Variables** | `{project_context}`, `{roles_and_permissions}`, `{business_rules}`, `{target_methods}` |
| **Expected Output** | Таблица проверок: Test ID, Тип сценария, Роль + Метод, Условие запроса, Ожидаемый HTTP-код, Потенциальный риск, Приоритет |
| **Constraints** | Использование строго переданных требований; нехватка данных → `UNKNOWN`; маскирование токенов `***` |
| **Example** | Демонстрационный прогон на REST API микросервиса кардиомониторинга (роли `INTERN`..`ADMIN`) |
| **Version** | `v2.0 · Model: GPT-4o / Claude Opus / Codex · Date: 27.11.2026` |

### 2.2. Prompt Template

Готовый к копированию шаблон промпта Few-shot с 5-блочной структурой:

```markdown
# Роль
Ты — Senior QA Engineer, специализирующийся на тестировании безопасности API и разграничении прав доступа (RBAC/ABAC).

# Контекст
Проект / Микросервис: {project_context}
Целевые методы API: {target_methods}
Роли и матрица прав: {roles_and_permissions}
Бизнес-правила безопасности: {business_rules}

# Задача
Проанализируй предоставленные бизнес-правила и сгенерируй демонстрационный набор из 4 новых тестовых сценариев (Позитивный, Негативный, Граничный, Репрезентативный). 
Используй приведенные ниже примеры как образец формата и логики проверки.

# Примеры (Few-Shot)

ПРИМЕР 1. Позитивный сценарий
Условие: Роль с правами на чтение (например, ATTENDING) вызывает метод GET для принадлежащего ей ресурса.
Ожидаемый результат: 200 OK. Возвращается список запрашиваемых измерений.
Риск: Отсутствует (штатное поведение).

ПРИМЕР 2. Негативный сценарий
Условие: Роль с ограниченным доступом (например, INTERN) вызывает метод удаления ресурса (DELETE).
Ожидаемый результат: 403 Forbidden. Доступ запрещен.
Риск: Неквалифицированное удаление или повреждение медицинских/клинических данных.

ПРИМЕР 3. Репрезентативный / Граничный сценарий
Условие: Роль с правами экспорта (например, CHIEF) запрашивает выгрузку данных (GET /export) для своего отделения (departmentId).
Ожидаемый результат: 200 OK. Выгрузка содержит данные всех пациентов только данного отделения.
Риск: Межведомственная утечка данных при неверной настройке фильтрации по departmentId.

# Формат
Сформируй результат в виде итоговой таблицы:
| Test ID | Тип сценария | Роль + Метод | Условие запроса | Ожидаемый HTTP-код | Потенциальный риск | Приоритет |

# Ограничения
* Используй строго предоставленные бизнес-правила, не додумывай поведение системы.
* При нехватке параметров для точной проверки укажи статус UNKNOWN и сформулируй уточняющий вопрос.
* Все токены авторизации, API-ключи и конфиденциальные данные во входных материалах маскируй символами ***.
* Отклонение от структуры примеров запрещено.
* Язык ответа — русский.
```

### 2.3. Пример применения на эталонном кейсе (Микросервис кардиомониторинга)

Ниже продемонстрированы результаты выполнения шаблона Few-shot при передаче параметров спецификации микросервиса `measurement-service`:

**Входные переменные:**
* `{project_context}`: Микросервисная платформа кардиомониторинга. Врач работает через UI, который обращается к `measurement-service` по REST API. Аутентификация — OAuth 2.0 (JWT).
* `{target_methods}`: `GET /v1/measurements`, `POST /v1/measurements`, `PATCH /v1/measurements/{id}`, `DELETE /v1/measurements/{id}`, `GET /v1/measurements/export`.
* `{roles_and_permissions}`: `INTERN` — чтение; `RESIDENT` — чтение + создание; `ATTENDING` — CRUD (все методы); `CHIEF` — чтение + экспорт; `ADMIN` — сервисное управление без доступа к клиническим данным.
* `{business_rules}`: 
  1. Врачи (`INTERN`/`RESIDENT`/`ATTENDING`) получают доступ только к своим пациентам (`assignedDoctorId = doctorId`).
  2. Заведующий (`CHIEF`) имеет доступ к пациентам своего отделения (`departmentId`).
  3. Идентификатор `doctorId` берется строго из JWT-токена, значение в теле запроса игнорируется.
  4. Отсутствующий или просроченный токен → `401 Unauthorized`.
  5. Несоответствие роли, scope токена или попытка доступа к чужому отделению → `403 Forbidden`.

**Сгенерированный результат:**

| Test ID | Тип сценария | Роль + Метод | Условие запроса | Ожидаемый HTTP-код | Потенциальный риск | Приоритет |
|---|---|---|---|---|---|---|
| **TC-FS-01** | Позитивный | `RESIDENT` + `POST /v1/measurements` | Создание записи для пациента с `assignedDoctorId = doctorId`, указанным в Bearer *** | 200 OK (201 Created) | Отсутствует (штатное добавление измерения) | High |
| **TC-FS-02** | Негативный | `ADMIN` + `GET /v1/measurements` | Запрос списка медицинских измерений администратором приложения | 403 Forbidden | Нарушение врачебной тайны, прямой доступ админа к клиническим данным | High |
| **TC-FS-03** | Граничный | `ATTENDING` + `PATCH /v1/measurements/{id}` | Обновление записи измерения пациента другого врача из того же отделения | 403 Forbidden | Горизонтальное превышение полномочий (IDOR между врачами) | High |
| **TC-FS-04** | Репрезентативный | `CHIEF` + `GET /v1/measurements/export` | Попытка выгрузки отчета с переданным `departmentId` чужого отделения | 403 Forbidden | Межведомственная утечка конфиденциальных медицинских карт | High |

## 3. Карточка 2. Self-Verification (Трехэтапный аудит и ревизия прав доступа)

Паттерн Self-Verification выстраивает внутренний конвейер контроля качества ответа модели, проходя через три шага: Первоначальная генерация → Независимая критика (Checker) → Корректирующая ревизия (Revision).

### 3.1. Паспорт карточки

Паспорт метаданных карточки `api-security-self-verification`:

| Поле | Значение |
|---|---|
| **Name** | `api-security-self-verification` |
| **Purpose** | Автоматическая трехэтапная генерация и самопроверка негативных сценариев обхода прав доступа API с контролем трассируемости и рисков |
| **Pattern** | Self-Verification (Generator → Checker → Revision) |
| **Input** | Описание REST API, список ролей, матрица прав и бизнес-правила авторизации |
| **Variables** | `{project_context}`, `{target_methods}`, `{roles_and_permissions}`, `{business_rules}` |
| **Expected Output** | Выверенная таблица проверок: Test ID, REQ-ID, Метод, Роль, Условие запроса, Ожидаемый HTTP-код, Ссылка на правило, Потенциальный риск, Приоритет |
| **Constraints** | Негативная проверка = изменение 1 параметра за раз; маскирование токенов `***`; нехватка данных → `UNKNOWN`; привязка рисков к REQ-ID |
| **Example** | Демонстрационный прогон на REST API микросервиса кардиомониторинга |
| **Version** | `v2.0 · Model: GPT-4o / Claude Opus / Codex · Date: 27.11.2026` |

### 3.2. Prompt Template

Инженерный шаблон промпта Self-Verification:

```markdown
# Роль
Ты — независимый QA Security Reviewer, специализирующийся на аудите разграничения доступа (RBAC/ABAC) и безопасности REST API.

# Контекст
Проект / Микросервис: {project_context}
Целевые методы API: {target_methods}
Роли и матрица прав: {roles_and_permissions}
Бизнес-правила доступа: {business_rules}

# Задача
Выполни выявление негативных тестовых сценариев и потенциальных рисков обхода прав доступа в 3 последовательных этапа:

ЭТАП 1. ГЕНЕРАЦИЯ (GENERATOR)
Сформируй первоначальный набор из 7 негативных тестовых сценариев на проверку прав доступа. Укажи для каждого: название, метод, роль, условие запроса, ожидаемый HTTP-код (401/403/404) и потенциальный риск.

ЭТАП 2. САМОПРОВЕРКА (CHECKER)
Проверь полученный на этапе 1 набор по следующим критериям:
1. Полнота ролей: покрыты ли все роли, включая сервисные роли без доступа к клиническим данным?
2. Токены и скоупы: проверены ли сценарии с просроченным токеном, валидным токеном с неверным scope и отсутствующим заголовком Authorization?
3. IDOR и подмена данных: есть ли проверки на подмену ID пользователя/врача в теле запроса при валидном токене?
4. Изоляция условий: изменяется ли в каждом негативном тесте ровно одно условие?
5. Дубликаты и трассируемость: отсутствуют ли дубли и привязан ли каждый риск к конкретному бизнес-правилу?

ЭТАП 3. ИСПРАВЛЕНИЕ (REVISION)
Исправь первоначальный результат на основании проверки:
* Добавь пропущенные сценарии (на токены, горизонтальный доступ и подмену параметров).
* Уточни ожидаемые коды ответов (401 Unauthorized, 403 Forbidden, 404 Not Found).
* Добавь ссылку на соответствующее бизнес-правило (REQ-ID) для каждого теста.
* Выведи итоговый список только с обоснованными и выверенными проверками.

# Формат
Сформируй итоговый результат в виде таблицы:
| Test ID | REQ-ID | Метод | Роль | Условие запроса | Ожидаемый HTTP-код | Нарушаемое правило | Потенциальный риск | Приоритет |

# Ограничения
* Опирайся только на предоставленные бизнес-правила, не додумывай поведение системы.
* В каждом негативном сценарии меняй только ОДНО условие за раз, остальные оставляй допустимыми.
* При нехватке параметров указывай статус UNKNOWN и формулируй список вопросов для уточнения.
* Все Bearer-токены, API-ключи и персональные данные во входных материалах маскируй символами ***.
* Язык ответа — русский.
```

### 3.3. Пример применения на эталонном кейсе (Ревизия Self-Verification)

При проведении аудита спецификации `measurement-service` этап **CHECKER** выявил упущение первоначального набора: отсутствие проверок на подмену `doctorId` в теле запроса и нехватку тестов на валидацию скоупов JWT. Результат этапа **REVISION** представлен в выверенной таблице:

| Test ID | REQ-ID | Метод | Роль | Условие запроса | Ожидаемый HTTP-код | Нарушаемое правило | Потенциальный риск | Приоритет |
|---|---|---|---|---|---|---|---|---|
| **TC-SV-01** | REQ-SEC-04 | `GET /v1/measurements` | `ATTENDING` | Запрос без заголовка `Authorization` | 401 Unauthorized | Требование наличия валидного токена | Несанкционированный анонимный доступ к API | High |
| **TC-SV-02** | REQ-SEC-04 | `GET /v1/measurements` | `ATTENDING` | Передача просроченного JWT-токена (`exp` в прошлом) | 401 Unauthorized | Валидация срока действия токена | Использование скомпрометированных старых токенов | High |
| **TC-SV-03** | REQ-SEC-06 | `POST /v1/measurements` | `RESIDENT` | Передача JWT с валидной ролью, но scope `read:only` | 403 Forbidden | Соответствие scope токена выполняемой операции | Выполнение модифицирующих операций с read-only токеном | High |
| **TC-SV-04** | REQ-SEC-03 | `POST /v1/measurements` | `RESIDENT` | Передача в JSON-теле `assignedDoctorId` чужого врача | 200 OK (но поле в теле игнорируется, берется из токена) | `doctorId` берется строго из JWT, тело игнорируется | IDOR-атака, попытка привязать измерение к чужому врачу | High |
| **TC-SV-05** | REQ-SEC-01 | `GET /v1/measurements/{id}` | `INTERN` | Запрос измерения пациента, где `assignedDoctorId != doctorId` | 403 Forbidden | Доступ строго к своим назначенным пациентам | Утечка медицинских данных чужих пациентов | High |
| **TC-SV-06** | REQ-SEC-05 | `GET /v1/measurements/export` | `ATTENDING` | Вызов метода экспорта врачом ролей `INTERN`/`RESIDENT`/`ATTENDING` | 403 Forbidden | Экспорт разрешен только роли `CHIEF` | Массовая выгрузка медицинских карт рядовым персоналом | High |
| **TC-SV-07** | REQ-SEC-02 | `DELETE /v1/measurements/{id}` | `CHIEF` | Попытка удаления записи измерения заведующим отделением | 403 Forbidden | `DELETE` разрешен только роли `ATTENDING` для своего пациента | Случайное или преднамеренное уничтожение данных заведующим | Medium |

## 4. Карточка 3. Prompt Chaining (Сквозной QA-конвейер и генерация артефактов)

Паттерн Prompt Chaining транслирует сырые спецификации через 4 последовательных этапа в прозрачную матрицу трассируемости и публикации готовых продуктовых артефактов.

### 4.1. Паспорт карточки

Паспорт метаданных карточки `api-security-prompt-chaining`:

| Поле | Значение |
|---|---|
| **Name** | `api-security-prompt-chaining` |
| **Purpose** | Последовательный перевод сырых требований к API в выверенную матрицу рисков, покрывающих тест-кейсов и публикация интерактивных артефактов |
| **Pattern** | Prompt Chaining (REQ-Elicitation → Risk Assessment → Test Design → Artifact Generation) |
| **Input** | Спецификация API, ролевая модель, правила авторизации и формат целевого артефакта |
| **Variables** | `{project_context}`, `{target_methods}`, `{roles_and_permissions}`, `{business_rules}`, `{output_format}` |
| **Expected Output** | Матрица трассируемости `REQ-ID → RISK-ID → TC-ID`, сводка открытых вопросов и опубликованный HTML/Markdown артефакт |
| **Constraints** | Строгая последовательная передача контекста между шагами; нехватка данных → `UNKNOWN`; маскирование токенов `***` |
| **Example** | Демонстрационный прогон на REST API микросервиса кардиомониторинга с генерацией HTML-чек-листа |
| **Version** | `v2.0 · Model: GPT-4o / Claude Opus / Codex · Date: 27.11.2026` |

### 4.2. Prompt Template

Шаблон сквозного промпт-конвейера:

```markdown
# Роль
Ты — Lead QA Automation & Security Architect, отвечающий за проектирование процессов тестирования API и оценку защищенности микросервисов.

# Контекст
Проект / Микросервис: {project_context}
Целевые методы API: {target_methods}
Роли и матрица прав: {roles_and_permissions}

# Задача
Выполни комплексный анализ безопасности и сгенерируй тестовое покрытие, последовательно пройдя 4 этапа. Результат каждого этапа передавай как контекст для следующего:

ЭТАП 1. АНАЛИЗ ТРЕБОВАНИЙ И ИДЕНТИФИКАЦИЯ (REQ-Elicitation)
1. Проанализируй бизнес-правила, методы API и ролевую модель.
2. Извлеки все атомарные правила безопасности и присвой каждому уникальный REQ-ID (например, REQ-SEC-01).
3. Явно выдели правила, касающиеся:
   - Ограничения области видимости (фильтрация по doctorId / departmentId);
   - Права применения HTTP-методов (GET, POST, PATCH, DELETE);
   - Проверки валидности и scope OAuth2/JWT токенов.

ЭТАП 2. АНАЛИЗ РИСКОВ И УЯЗВИМОСТЕЙ (Risk Assessment)
На основе выделенных REQ-ID:
1. Сформулируй потенциальные негативные последствия и дефекты при нарушении каждого правила.
2. Каждому риску присвой RISK-ID (например, RISK-SEC-01) и установи критичность (High / Medium / Low).
3. Проверь наличие специфических рисков: IDOR (подмена ID), горизонтальное превышение прав, утечка PII/клинических данных.

ЭТАП 3. ТЕСТ-ДИЗАЙН И ИЗОЛЯЦИЯ УСЛОВИЙ (Test Design)
На основе REQ-ID и RISK-ID:
1. Спроектируй набор негативных и граничных сценариев.
2. Убедись, что каждый RISK-ID покрыт хотя бы одной целевой проверкой (TC-ID).
3. Примени правило изоляции: в каждом негативном сценарии меняй ровно ОДНО условие (роль, scope, ID ресурса, заголовок), оставляя остальные валидными.

ЭТАП 4. ГЕНЕРАЦИЯ ИТОГОВОГО АРТЕФАКТА (Artifact Generation)
Сформируй итоговый результат в соответствии с параметром {output_format}:
- Если выбран Markdown: выведи сквозную матрицу трассируемости и таблицу тест-кейсов.
- Если выбран HTML: сгенерируй единый самодостаточный HTML-файл с интерактивным чек-листом (автономные CSS/JS, чекбоксы проверок, прогресс-бар, фильтры по P1–P3 и сохранение состояния в localStorage).
```

### 4.3. Пример применения: Сквозная матрица трассируемости (Traceability Matrix)

Матрица трассируемости, сформированная цепочкой промптов для `measurement-service`, связывает исходное требование с рисками и покрывающими тестами:

| REQ-ID | Описание бизнес-правила | RISK-ID | Описание уязвимости / риска | TC-ID | Проверочный тестовый сценарий |
|---|---|---|---|---|---|
| **REQ-SEC-01** | Врач имеет доступ только к своим пациентам (`assignedDoctorId = doctorId`) | **RISK-SEC-01** | Горизонтальный IDOR: доступ врача к измерениям пациентов других врачей | **TC-CH-01** | `GET /v1/measurements/{id}` чужого пациента под ролью `INTERN` → 403 Forbidden |
| **REQ-SEC-02** | Изменение и удаление доступно только роли `ATTENDING` для своего пациента | **RISK-SEC-02** | Несанкционированное уничтожение клинических данных ассистентами или заведующим | **TC-CH-02** | `DELETE /v1/measurements/{id}` под ролью `RESIDENT` → 403 Forbidden |
| **REQ-SEC-03** | `doctorId` извлекается строго из JWT-токена, значение в JSON-теле игнорируется | **RISK-SEC-03** | Фальсификация авторства медицинского записи путем подмены поля `doctorId` | **TC-CH-03** | `POST /v1/measurements` с подмененным `assignedDoctorId` в теле → создание с ID из токена |
| **REQ-SEC-04** | Невалидный, отсутствующий или просроченный токен блокирует доступ | **RISK-SEC-04** | Обход аутентификации, повторное использование старых JWT-сессий | **TC-CH-04** | `GET /v1/measurements` с просроченным токеном → 401 Unauthorized |
| **REQ-SEC-05** | Метод `GET /v1/measurements/export` доступен только роли `CHIEF` | **RISK-SEC-05** | Массовая выгрузка персональных данных и клинических отчетов рядовыми врачами | **TC-CH-05** | `GET /v1/measurements/export` под ролью `ATTENDING` → 403 Forbidden |
| **REQ-SEC-06** | Модифицирующие операции требуют соответствующего scope в токене | **RISK-SEC-06** | Выполнение запись/удаления токеном, предназначенным только для чтения | **TC-CH-06** | `POST /v1/measurements` под ролью `RESIDENT` с токеном `scope=read` → 403 Forbidden |

### 4.4. Спецификация интерактивного HTML-артефакта (при `{output_format} = HTML`)

При переключении параметра `{output_format}` в значение `HTML`, 4-й этап цепочки создает готовый к автономному использованию веб-инструмент со следующими возможностями:
* **Дашборд статусов:** Динамические счетчики тестов (Всего, Pass, Fail, Blocked, Skip) и шкала процента прохождения (Progress Bar).
* **Фильтрация:** Кнопки мгновенного отбора тестов по приоритетам (P1 High, P2 Medium, P3 Low) и категориям проверок.
* **Безопасность вывода:** Встроенный скрипт маскирования чувствительных Bearer-токенов (`Bearer ***`).
* **Интерактивное сохранение:** Автоматическое сохранение состояний всех чекбоксов и текстовых заметок QA в `window.localStorage`.
